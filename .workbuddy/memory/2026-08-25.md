## 小红书 Skill "链接全失效/无正文" 二次修复（2026-08-25 17:45→18:05）

### 用户反馈（新版本）

### 根因 1：Windows console gbk 编码（最致命）
Python 脚本用 `sys.stdout.write(json.dumps(items))` 输出含中文 JSON。Windows 默认 gbk，遇到 `❗` U+2757 / `🤤` 等生僻汉字抛 UnicodeEncodeError → exit(1) → Java IOException → 友好提示或多次重试失败。

**修复**：脚本里 `sys.stdout.reconfigure(encoding='utf-8')` + Java ProcessBuilder 环境 `PYTHONIOENCODING=utf-8` + `PYTHONUTF8=1`，**三重保险**。

### 根因 2：详情页只抓前 5 篇
默认 `--detail 5`，但 `top=8` 时后 3 篇没正文。

**修复**：默认 `--detail 8`（与 topN 一致）。

### 根因 3：Java 正则 `\W` 把中文 strip 掉（隐 bug）
代码 `body.replaceAll("^[\s\W_]+", "")` 想清开头标点，但 Java `\W` = `[^a-zA-Z0-9_]`，**中文字符全部匹配 `\W`**，结果如果内容开头是中文，整段都被当 leading chars 全部 strip 掉直到第一个 ASCII 字母/数字——很多纯中文笔记整段被 strip 成空字符串。

**修复**：改用 Unicode 属性 `^[\p{P}\p{S}\s]+`（只 strip 标点 Punctuation / 符号 Symbol / 空白 Space，不碰中文）。

## 小红书 Skill 第三次增强：IOException 重试机制（2026-08-25 18:10）

### 根因
单次采集可能因为瞬时问题失败：
- Playwright 启动开销导致 120s 超时偶尔碰到
- Python 进程偶发 exit != 0（白屏 / 风控 / 等元素超时）

### 修复（XhsCollector.java 重构 search）
- 把原来一次性的 search 拆成两层：
  - 外层 `search()` 循环 2 次（attempt=1, 2）
  - 内层 `runScriptOnce(kw, attempt)` 是单次 ProcessBuilder 调用
- 第 1 次抛 IOException → 重试时打了"重试中..."日志 → 第 2 次成功就直接 return
- 第 2 次仍失败 → 抛最后一次的 IOException（已经被 BotMain 包成友好提示）
- exit != 0 时把 stderr 尾部 200 字打到自己的 stderr，但不外泄——方便排查："Python 退出码 X，stderr 尾部: ..."

### 与 BotMain 的 catch 链条确认
- XhsCollector.search 抛的 IOException 文本都是中文友好（"暂时没有获取到..." / "超时..." / "失败..."）——绝无英文技术词
- BotMain.handleXhsGuide catch Exception 统一返 "😅 暂时没有获取到相关攻略内容，请稍后再试～（若多次失败，可能是 cookie 过期，更新即可）"
- 用户在微信里看到的是友好中文，stderr 里的类名（IOException）只在 IDE Run 面板可见

## 小红书 IOException 根因深挖：pipe buffer 阻塞 + 进程独占（2026-08-25 18:25）

### 用户新反馈（截图）
- "[XhsCollector] 第 1 次失败: ... 重试中..."  ← 重试机制跑起来了
- "[XhsCollector] 第 2 次失败"  ← 还是超时
- "[小红书] 采集失败 (...)"  ← 上抛后被 catch
- 但**直接跑脚本只要 31s**，bot 调要 120s+ 才能超时

### 根因 1（关键）：Java ProcessBuilder pipe 缓冲阻塞
Python 默认 stdout 是 block-buffered（8KB 块），连接到 pipe（不是 tty）时尤其严重。
脚本要输出 11KB JSON，正常 flush() 已经做了。但：
- Java 进程启动 Python 后**没立刻读 stdout**
- 当 stdout 累积到 pipe 上限（Windows ~64KB 浮动）后，Python 写下一个 chunk 会阻塞
- 后续即使 Python 正常写，但 stdout 写满后 `sys.stdout.write() -> write()` 也会卡
- Java 在 `waitFor(120s)` 期间一直没读 pipe → Python 等到 120s 才被 destroy

**修复**：
- 加 `PYTHONUNBUFFERED=1` 环境变量（Python 强制 line-buffered）
- Java 起守护线程**主动读 stdout / stderr**（drainIntoBuffer / drainToErr）→ 杜绝 pipe 阻塞
- drainOut 收集到 ByteArrayOutputStream，waitFor 完成后转 String

**测试验证**：写了 1MB（>pipe buffer）的 Python 输出，drain 守护线程在 1.15s 内全部读完，无超时。

### 根因 2（次要）：180s 超时不够
慢网 / 8 篇详情下偶尔会超 120s。改成 180s（3 分钟）更稳，错误消息明示："小红书攻略获取超时（180s），请稍后重试或换个关键词"。

### 经验教训
- **永远别假设子进程的 stdout 会自动 flush 给 parent**。Java/Node 启动子进程时，应在 waitFor 同时或之前**起守护线程读 pipe**，否则一旦 pipe 满就是隐性死锁
- `PYTHONUNBUFFERED=1` 是 Python 友好的"防呆"环境变量
- timeout 设置宁大勿小（180s 优于 120s），反正有重试兜底

## 小红书"无关链接/查询失败"根治（2026-08-26 上午，第 4 次修复）

### 用户反馈

2. **无关链接来源 A：buildXhsKeyword 无城市时裸搜主题词**

## 小红书"微信点不开链接"修复（2026-08-26 11:30）

### 用户反馈
"弹出来的链接是相关的，但是链接直接用微信点不开"——手机微信内置浏览器打开链接显示"你访问的页面不见了"。

### 根因（已知，不可绕过）
- **小红书对未登录用户一律返回"页面不见"**（反爬机制，不是 bot 错）
- 微信内置浏览器没有小红书登录态 → 不管 search_result 还是 explore URL 都"页面不见"
- xsec_token 不能解决（需要 cookie 登录态）

### 修复方案
1. **长链转 xhslink 短链**（XhsCollector.toXhsShortLink）：
   - 提取 search_result 或 explore URL 里的 24 位 hex note_id
   - 输出 `http://xhslink.com/o/<id>` 短链
   - 微信里点 xhslink 走 OAuth 授权（302 → open.weixin.qq.com → 小红书），至少不会被屏蔽"页面不见"
   - 绑定了小红书微信账号的用户 OAuth 后到小红书（可能到首页/笔记）
2. **format 文案重做**（用户友好引导）：
   - 明确说"微信里点不开是正常的（小红书对未登录用户一律「页面不见」）"
   - 教用户 ① 复制"标题+作者"到小红书 App 搜 ② 复制链接到浏览器打开（需登录）
   - 强调"上面的 📝 正文摘要已经可以直接读，无需点链接"
3. **正文摘要 350 → 500 字**：用户不点链接也能获取更多核心内容（店名/地址/玩法）

### E2E 验证
"南京美食" 28s：8 条全南京+500字摘要+店名+地址+xhslink 短链。
示例 URL：`http://xhslink.com/o/6a80575c0000000026037f2c`

### 经验
- 在反爬严格的内容平台（小红书/B站/抖音），**bot 应把"内容抓回直接展示"作为主要交付**，链接只是 bonus
- 微信内浏览器几乎无法访问需要登录态的平台 → 用 OAuth 短链（xhslink）兜底
- 教用户"在小红书 App 搜"比"点链接"更可靠
